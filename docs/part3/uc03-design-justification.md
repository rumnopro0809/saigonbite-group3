## 3.2 Comparison of Part 2 Design vs. Final Part 3 Implementation

| Design Area | Part 2 Planned Design (`docs/part2/`) | Final Part 3 Implementation (`main`) | Justification for Keeping or Adjusting |
| :--- | :--- | :--- | :--- |
| **Hub entity (`architecture.md`, `CRC07`)** | Hub with location, `Capacity > 0`, active/deleted flags, `RowVersion` | Shared `Hub` entity in `SaigonBite.Domain.Entities` with `Name`, `Address`, `District`, `MaxCapacity`, `IsActive`, `IsDeleted`. `RowVersion` was added by the additive migration `Uc03HubRowVersion`, together with the check constraint `CK_Hubs_MaxCapacity_Positive`. | The first UC03 prototype used its own `AppDbContext` and a `Location`/`Capacity` hub. Before merging, it was ported onto the team schema so that UC01 order placement and UC03 hub management read the same rows. "Location" is split into `Address` and `District` to match the team ERD. The migration only adds columns and a constraint; it does not edit `InitialCreate`. |
| **Positive capacity (`FR14.1`, `BR8` denominator)** | Team proposal: capacity must be a positive integer | Enforced twice: `HubValidator` rejects `MaxCapacity <= 0` before saving, and the database check constraint rejects it if any other code path tries. | BR8 divides by capacity, so 0 would cause a division by zero and a negative value would make the load meaningless. The rule is still a team assumption awaiting instructor confirmation (see "Open assumptions"). |
| **Hub load (`FR02`, `BR7`, `BR8`, `CRC07`)** | `(Confirmed + Preparing) / Capacity`, derived and never stored | `Domain/HubLoad.cs` classifies the load as Quiet (< 30%), Normal (30% to < 90%) or Full (≥ 90%). `HubLoadService` counts only `Confirmed` and `Preparing` orders. This is the same definition as `OrderService.CalculateHubLoad` in UC01, and a test checks that both give the same number. | One definition is used for order acceptance, the Quiet Kitchen discount, the hub list and R2. As a result, the percentage the Admin sees is the same one that decides whether a new order is accepted. Load is never written to the database, so it cannot drift. |
| **Hub CRUD and concurrency (`FR14.1–FR14.4`)** | `HubService` with rowversion checks; soft-delete; no cascade delete | `Infrastructure/Services/HubService.cs` creates a hub and its `HubBrand` links in one transaction. Update, set-active and delete require the `RowVersion` the Admin loaded, and a stale, missing or malformed value returns `Conflict` without changing anything. Delete sets `IsDeleted` and keeps the orders and history. | The services are in `Infrastructure` rather than `Application` because the team's `Application` project does not reference EF6. The validator and DTOs stay in `Application/Hubs`. Optimistic concurrency avoids locking and still prevents two Admins from overwriting each other's edits. |
| **Inactive or deleted hub (`FR14.4`)** | Stop new orders; existing kitchen and shipper work continues | A hub with `IsActive = false` or `IsDeleted = true` is rejected by UC01 `OrderService.Quote` with `NOT_FOUND`. Orders already in progress keep their status and can still move through the lifecycle. Reactivating a hub accepts new orders again. | This keeps the customer from ordering from a kitchen that is closed, without breaking deliveries already on the way. This operational behaviour is a team proposal (use case 2.2.3) awaiting confirmation. |
| **Heavy-rain flag (`FR16`, `BR5`, `BR17`)** | Global `SystemSetting`, snapshot on each order | `RainSettingService` reads and writes the single `SystemSetting` row with a `RowVersion` check. The flag is only read when a new order is quoted; existing orders keep their `HeavyRainSnapshot`. | Changing the flag must never change the price of an order that has already been placed (BR17). A test places an order, flips the flag, and checks that the old order is unchanged while a new quote uses the new flag. |
| **Admin UI transport** | Part 2 prototype planned REST endpoints (`PUT /api/rain-flag`, Web API 2) | No Web API. The three buttons on the hub pages (rain flag, stop/resume orders, soft-delete) send a form POST with an anti-forgery token to `HubsController` and get JSON back (`Scripts/uc03.js`). | Web API 2 would have needed a second authentication setup next to the HT01 session login. Reusing the MVC controller keeps one login, one anti-forgery check and one role filter for every UC03 page. |
| **Controller naming and R2 location** | `AdminHubsController`; R2 inside a shared `ReportsController` | `HubsController` (inherits `Uc03Controller`, which carries `[AdminOnly]`), and R2 in `HubReportsController.HubUtilization`. | HT02 already owns `ReportsController` for R1. A separate controller avoids merge conflicts and keeps each report's owner clear. The shared base class `Uc03Controller` keeps the Admin check in one place. |
| **Authentication and authorization (`NFR04`)** | Server-side role checks; HT01 login | `[AdminOnly]`, `[KitchenOnly]` and `[ShipperOnly]` (`Security/RoleOnlyAttribute.cs`) check `Session["CurrentUserId"]` set by the HT01 `AccountController`, and confirm the user is active and has the right role. The services check again: the kitchen only sees its own hub (via `StaffProfile`), and a shipper only sees orders where `ShipperId` is their own. | The first prototype had separate login pages for Admin, kitchen and shipper. They were removed so that every role signs in at `/Account/Login`, which is owned by HT01. Checking again in the service means that a hand-crafted POST cannot act on another hub's or another shipper's order. |
| **Kitchen board (`FR17`, `BR15`, `BR16`)** | Kitchen actions go through `OrderTransitionService` | `KitchenBoardService` lists the own hub's active orders oldest first and passes Confirm, Start preparing, Mark ready and Reject to UC01 `OrderTransitionService`. Reject needs a reason and refunds a paid online order. | No status change is written directly by UC03. Every transition goes through the single state machine, which also writes `OrderStatusHistory` in the same transaction (NFR06). |
| **Shipper dispatch (`FR17`, `BR14`, `BR15`, `AMB01`)** | AMB01: Admin assigns a shipper to a Ready order | `ShipperService.AssignShipper` only accepts `Ready` orders and active shippers, and can reassign before pickup. The shipper page offers Pick up, Delivered (COD needs "cash collected") and Failed (needs a reason). | AMB01 is implemented as written. The COD error code is `BR15`, the same code UC01's `OrderTransitionService` uses, so the customer and staff see one consistent message. Part 2 linked the cash check to BR14; the RTM records both codes. |
| **R2 Hub Utilization (`FR19`, `AMB06`)** | Handled count, Confirmed→Ready mean, Quiet Kitchen count, current load | `HubReportService` uses Vietnam-time day boundaries. "Handled" means the order was ever Confirmed in the range, including orders cancelled later. The mean preparation time uses only orders with both a Confirmed and a Ready history row, and is shown as "no data" (not 0) when there is none. The Quiet Kitchen count comes from each order's snapshot. Current load reuses `HubLoadService`. Soft-deleted hubs are left out. | This follows AMB06 in `architecture.md`. Showing "no data" instead of 0 minutes avoids a misleading average (use case 2.2.3, exceptions). |
| **Bilingual UI (`NFR03`)** | VI/EN toggle | UC03 views use `HubText` with the shared `sb_lang` cookie. `Web.config` sets `globalization fileEncoding="utf-8"` so that Vietnamese text in views without a BOM displays correctly. | It uses the same cookie as UC01 and UC02, so the language choice holds across the whole site. |

## Change Request Readiness

- **New hub attribute, such as opening hours:** add the column with an additive migration, extend `HubInput`, `HubValidator` and the form. `HubLoadService` and R2 are not affected.
- **Different load thresholds:** change the two constants in `Domain/HubLoad.cs`. Order acceptance, the discount and the hub list all read the same class, and `HubServiceTests` checks the boundaries.
- **Automatic shipper assignment instead of AMB01:** replace the Admin call to `ShipperService.AssignShipper` with an automatic picker. Pick up, Delivered and Failed are not affected.

## Open assumptions (awaiting instructor confirmation)

1. Capacity must be a positive integer (`FR14.1`).
2. A deactivated or deleted hub rejects new orders but lets existing orders finish (`FR14.4`).
3. The R2 definitions follow AMB06.
4. Removing a brand from a hub may leave an old `Placed` order of that brand hard to edit. How to handle this is still open (use case 2.2.3, Update step 3).
