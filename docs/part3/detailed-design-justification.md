## 3.2 Comparison of Part 2 Design vs. Final Part 3 Implementation

| Design Area | Part 2 Planned Design (`docs/part2/`) | Final Part 3 Implementation (`feat/uc01-orders`) | Justification for Keeping or Adjusting |
| :--- | :--- | :--- | :--- |
| **Solution & Layering (`ADR-001`, `architecture.md`)** | 5 projects: `Domain`, `Application`, `Infrastructure`, `Web`, `Tests` on `.NET Framework 4.8` / ASP.NET MVC 5 / EF6 Code First | 5 classic MSBuild `.csproj` projects targeting **`.NET Framework 4.7.2`** (with `PackageReference`), `ASP.NET MVC 5.2.9`, `Entity Framework 6.4.4`, `Bootstrap 5`, `MSTest 2.2.10`. `Domain` and `Application` have **zero** references to `EntityFramework` or `System.Web`. | The lab/development machine has the `.NET Framework 4.7.2` targeting pack installed with VS 2019 MSBuild; ASP.NET MVC 5 and EF 6.4.4 are identical on 4.7.2 and 4.8 (`Tier 3` requirement fully preserved). Keeping `Domain` and `Application` free of EF6/Web lets all 38 pure unit tests run in `< 1 ms` without a database or browser (`NFR02`). |
| **Where Pricing & Lifecycle Live (`CRC02`, `CRC05`)** | `PricingService` and `OrderLifecycle` isolated in business/service layer, never in controllers, views, or EF entities | `PricingService` (`BR1–BR14`) and `OrderLifecycle` (`BR15–BR17`) remain pure C# classes in `SaigonBite.Domain`. Application defines `IOrderService` and `IOrderTransitionService` contracts/DTOs; EF6 implementations `OrderService` and `OrderTransitionService` live in `SaigonBite.Infrastructure.Services`. | Preserves strict single-source-of-truth pricing and state-machine guards while avoiding leaking `System.Data.Entity` into `SaigonBite.Application`. Controllers only bind HTTP inputs/ViewModels and delegate all decisions to services. |
| **Payment Strategy Pattern (`CRC03`, `domain-and-payment.puml`)** | `IPaymentStrategy` + 5 concrete classes (`MoMoStrategy`, `VNPayStrategy`, `ApplePayStrategy`, `PayPalStrategy`, `CodStrategy`) + `PaymentSelector` | Implemented exactly as designed in `SaigonBite.Application.Payments`, plus one small internal base class `SimulatedOnlinePaymentStrategy` shared by the 4 online simulated adapters (`MoMo`, `VNPay`, `ApplePay`, `PayPal`). `PaymentSelector` resolves strategies from an injected `Dictionary<PaymentMethod, IPaymentStrategy>` after invoking `PricingService.ValidatePayment` (`BR13–BR14`). | Extracting `SimulatedOnlinePaymentStrategy` removes duplicated correlation-key/timestamp boilerplate across the 4 simulated online gateways without changing the public Strategy contract. Adding a new payment method requires only adding a new `IPaymentStrategy` class and registering it — existing 5 strategy classes remain untouched (`NFR02`). |
| **Relational Schema & EF6 Migrations (`database-erd.puml`, `architecture.md`)** | 14 tables (`User`, `LocalProfile`, `TouristProfile`, `StaffProfile`, `Hub`, `Brand`, `HubBrand`, `MenuItem`, `Voucher`, `SystemSetting`, `Order`, `OrderLine`, `PaymentRecord`, `OrderStatusHistory`); single schema for customers; `decimal(19,4)`; `datetimeoffset`; soft-delete; no cascade delete | All 14 entities mapped in `SaigonBiteDbContext` via Fluent API with `HasPrecision(19, 4)` on all currency columns, composite PK `(HubId, BrandId)` on `HubBrand`, shared-PK 1:0..1 on `LocalProfile`/`TouristProfile`/`StaffProfile`, unique indexes on `Users.Identifier`, `Vouchers.Code`, `Orders.OrderCode`, `RowVersion` (`[Timestamp]`) on `Order`, and `WillCascadeOnDelete(false)` on all foreign keys. Tracked via scaffolded EF6 migration `202611240719260_InitialCreate` + idempotent `SaigonBiteSeeder`. | Matches the Part 2 ERD 1-to-1. Disabling cascade delete protects historical `OrderLines`, `PaymentRecords`, and `OrderStatusHistories` when Admins soft-delete hubs, brands, menu items, vouchers, or users. Explicitly referencing `SqlProviderServices` ensures `EntityFramework.SqlServer.dll` copies reliably on clean builds. |
| **Hub Load Derivation (`FR02`, `BR8`, `CRC07`)** | Derived count `(Confirmed + Preparing) / MaxCapacity`; never stored manually; reject `>= 90%` and suggest alternative hubs | `OrderService.CalculateHubLoad` counts strictly `OrderStatus.Confirmed` and `OrderStatus.Preparing` divided by `MaxCapacity`. When `PricingService.Calculate` throws `BR8`, `OrderService.Quote` calls `FindAlternativeHubNames` to suggest active hubs below `90%` load. | During QA review, an initial draft that accidentally included `Placed` and `Ready` was caught and corrected (`74081c9`) to match `BR8` and `architecture.md` exactly. |
| **UC01 Runtime Protections (`FR01–FR07`, `D01`, `D05`, `AMB03`, `AMB05`)** | Atomic placement (`NFR05`), quote-drift warning (`D01`), idempotent submission (`D05`), Placed-only edit reusing frozen snapshot (`BR17`), frozen existing-line prices (`AMB03`), online edit charge/refund (`AMB05`), full simulated refund on cancel (`BR16`) | All implemented in `OrderService` and `OrderTransitionService` inside explicit `DbContextTransaction` blocks (`PlaceOrder`, `EditOrder`, `Transition`) with `RowVersion` optimistic concurrency checks, `RequestKey` duplicate guard, `ExpectedPayableTotal` `QUOTE_CHANGED` guard, and `OrderStatusHistory` written in the same transaction (`NFR06`). | Guarantees zero partial orders, zero double charges on double-click retries, no silent price drift, and reproducible historical totals even after menu price or heavy-rain changes. |
| **Razor Views & Temporary Demo Switcher (`NFR03`, `NFR04`)** | Responsive Bootstrap UI with VI/EN toggle and server-side authentication (`HT01`) | Bootstrap 5 views (`_Layout`, `Home/Index`, `Orders/{Create,Index,Details,Edit}`) with `sb_lang` cookie VI/EN toggle and `[ValidateAntiForgeryToken]`. `DemoSessionHelper` stores `Session["CurrentUserId"]` so UC01 can be tested independently across all 5 seeded roles before merging `HT01` (`AccountController`). | Razor views on classic ASP.NET MVC 5 without Roslyn CodeDom compile with C# 5 (`csc.exe`), so views deliberately avoid C# 6 syntax (`?.`, `$""`). Using `Session["CurrentUserId"]` aligns directly with `feature/uc02-menu` (`AccountController`) for seamless merge. |

## 3.3 Change Request Readiness Note (Week 5)

> **Status:** Awaiting confirmation of the official Week 5 Change Request prompt from the instructor. No artificial or unissued Change Request has been fabricated in this branch.

The current codebase is structurally prepared to absorb the Week 5 Change Request with localized changes:
- **If a new payment method is requested:** Create one new class implementing `IPaymentStrategy` (or extending `SimulatedOnlinePaymentStrategy`) in `SaigonBite.Application/Payments/`, add the enum value / customer eligibility rule in `PricingService.ValidatePayment`, and register the new strategy in `PaymentSelector.CreateDefault()`. **Zero lines** need to be edited in `MoMoStrategy.cs`, `VNPayStrategy.cs`, `ApplePayStrategy.cs`, `PayPalStrategy.cs`, or `CodStrategy.cs` (verified by `PaymentStrategyTests.PaymentSelector_InjectedCustomStrategy_ResolvesWithoutEditingExistingAdapters`).
- **If a pricing rule adjustment is requested:** All pricing rules live solely inside `PricingService.Calculate`, with zero duplicated formulas in `OrderService`, `OrdersController`, or Razor views, so a rule change updates one pure class and its MSTest boundary suite.
